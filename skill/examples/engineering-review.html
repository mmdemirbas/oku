    Structured Logging Migration — From console.log to pino

    A worked example of the html-doc skill. The topic — migrating a TypeScript HTTP service from ad-hoc logging to a structured JSON logger — is fictional but realistic. The point is to show how the engineering-review narrative arc, the component kit, and the chrome layout look when applied to a concrete review.

    14 May 2026 · Audience: service team · Read time ~10 min
    TL;DR

    One paragraph, then five points

    Replacing scattered console.log calls with a structured logger (pino) gives the team queryable logs and correlation IDs at the cost of a one-week migration. The shape of the work matches the code-mod pattern; the open question is request-context propagation.

    • Why now: on-call has spent 14 hours over four incidents grepping plain-text logs in the last quarter.
    • What changes: log calls go from positional strings to object-first logger.info({ user_id }, "message").
    • What stays: log levels, log destination, dashboard queries (they get easier, not different).
    • Effort: ~3 days code-mod, ~2 days context plumbing, ~1 day cutover.
    • Open question: AsyncLocalStorage vs explicit req.logger handoff — covered in §6.

    §1Foundations

    Quick refresher on the relevant terms; skip if you've shipped a structured logger before.

    Structured logging means every log line is a single JSON object with a stable schema: { "level": "info", "msg": "...", "user_id": 42, "request_id": "..." }. Compare to traditional logging, which emits a freeform string like "info: user 42 requested resource ..." — the same data, but no machine can filter on user_id without a regex.

    PinoPino is a low-overhead Node.js logger that emits NDJSON to stdout. Designed to keep hot paths fast: serialisation happens in a child process or after the request returns. is one of three plausible libraries (WinstonWinston is a more flexible/configurable logger but with higher per-call overhead. Trade-off: more transports out of the box, slower hot path., BunyanBunyan is the original JSON logger for Node; mostly superseded by Pino but still used in long-lived services., pino). The decision is in §5.

    The three concrete pain points:

    1. No correlation across services. A request crossing the API gateway → service A → service B can't be reconstructed without timestamp alignment, because no correlation ID is attached.
    2. No filtering by attribute. Splunk and CloudWatch Insights both parse JSON natively but get nothing useful from "user 42 requested ..." strings.
    3. No type discipline. Half the team writes console.log(user, action) (positional, fragile); the other half writes console.log(\`user $\{user\} did $\{action\}\`). Schemas drift; downstream regex breaks weekly.

    §3The solution shape

    Adopt pino with a request-scoped child logger. AsyncLocalStorage carries the request context through the call chain, so any code path can log request_id + user_id without explicit threading. 

    // Before
console.log(\`user $\{user.id\} updated profile\`);

// After
req.log.info({ user_id: user.id, action: "update_profile" }, "profile updated");

    Headline shape: every log line is a JSON object whose first argument is the structured payload, second is a human-readable message. The request context (request ID, user ID, route) is bound to a child logger created in the request middleware; downstream code uses req.log instead of importing a global logger.

    §4Components

    Three load-bearing pieces. Built and reviewed in dependency order.

    4.1 Logger module (lib/logger.ts)

    Single source of truth. Exports a configured pino instance plus a factory for child loggers. Sets base fields (service, version, environment) once at boot.

    4.2 Request middleware

    Generates a request ID per inbound HTTP request, attaches a child logger to req, and registers it in AsyncLocalStorage so deeper code (queue consumers, DB hooks) can pick it up without a parameter.

    4.3 Code-mod across handlers

    Every console.* call in src/handlers/** becomes a req.log.* call. A jscodeshift codemod handles 90% mechanically; manual review for the 10% that need new structured fields (e.g. splitting a message into action + resource attributes).

    Why request middleware, not a per-call import? · click to expand

    A global import { logger } from './lib/logger' at every call site works for the level and base fields, but it can't carry per-request context. The same log line ends up with no request_id, so you've structured the data but lost the correlation — solving 2 of 3 pain points instead of 3.

    AsyncLocalStorage means the request context follows the call chain even into async hooks. Cost: a single import at the entry point; no boilerplate in handlers.

    §5Decisions and rejected alternatives

    5.1 Library choice: pino vs Winston

    Winston (rejected)

    • More configurable, more transports, but ~10× per-call CPU cost in synchronous mode.
    • Async mode is opt-in and fiddly.
    • Stronger ecosystem of transports we don't need.

    Pino (chosen)

    • Fastest by ~5× on hot paths; serialisation off the request thread.
    • Defaults to NDJSON, fits our log shipper.
    • Same on-prem stack the platform team already uses.

    5.2 Context propagation: AsyncLocalStorage vs explicit handoff

    Open question — see §6

    We've leaned toward AsyncLocalStorage in the prototype, but it has one sharp edge with Node's worker threads. If the service ever spins up worker threads, the request context doesn't follow. The explicit-req.logger path is more verbose but bulletproof.

    §7Future / FAQ

    Do we have to migrate everything before turning it on?

    No. pino and console can coexist; both write to stdout. The shipper parses NDJSON if present and falls back to plain text. The migration can ship per-handler.

    What about the existing log retention rules?

    Retention is set by the shipper, not the logger. Same 14-day hot / 90-day cold split; no platform-team change needed.

    Can we still log objects? console.log(err) is a habit.

    Yes: req.log.error({ err }) uses pino's built-in error serialiser and you get the full stack, message, and properties as JSON fields. Cleaner than console.log(err), which serialises differently in every runtime.
