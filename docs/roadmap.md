> [!TLDR]
> Most of the chart kit is interactive — tooltips, click-pin, cursor sweep, fullscreen-preserving lightbox, deconflicted labels, family-grouped catalog with clickable mini-cards. Open work is exploratory: auditing hover feedback per chart type, and the catalog and reactive-prose research.
>
> - Interactivity coverage: every variant in the table below fires a contextual tooltip on hover with real per-anchor data. Cartesian + ridgeline + sparkline + gauge carry a synced cursor that updates the tooltip per-position.
> - Visual polish: quadrant + bubble label deconfliction is no-fly-zone aware. Parallel-coordinates line stroke 3.6 → 5px with fade-others on hover. Donut/pie pinned slices scale + accent-stroke. Mermaid fonts clamped to 13px, aspect-fit caps tall portrait diagrams.
> - Layout: source / render columns box-top aligned across every example-pair on reference / charts / tables — zero pixel delta.
> - Tooltip: width-stable across pin states; explicit × close button when pinned; `_tipPinned` flag stops cursor-driven charts from overwriting pinned content.
> - Pick-by-family: 43 clickable mini-cards each with a tiny live render — readers scan the shape they want and click straight into the variant's full example.
> - Robustness is the other half of the board: vendored typography, an atomic
>   build, listener teardown, a keyboard-reachable sidebar collapse. Thirteen
>   items, filterable by area and priority below.
> - `oku` is on PATH as a system command (uv tool install).

## Recent landings {#recent}

- The last exploring row is answered, and the answer is that half of it already ships and nobody can find that half. The row asked for `${expr}` interpolation and `oku-bind` two-way binding. **The blocker is not the one that would be assumed**: a built page carries no CSP at all — measured, `new Function('return 6*7')()` returns 42 on a standalone page opened over `file://` — so an evaluator would run fine. It also corrected a comment in the browser suite's own wait helper, which had been citing that non-existent CSP as a design reason for three releases; the decision it defends is still right for its other reason, and the wrong half is gone. What the row wanted is mostly reachable today: `{{key}}` personalization substitutes reader-set values into prose at runtime, and an HTML island in a page executes its own `<script>`, so binding a form input needs no new syntax. Against that, `${expr}` would add a templating layer in the renderer and a second evaluation surface in a kit that spent real effort making a viewed document inert. The decision and its reopen trigger are recorded under [Locked decisions](#decisions) rather than here, because that is where a question goes once it has an answer. **And the finding worth more than the decision**: `{{key}}` personalization — the gear icon in the chrome cluster, the localStorage-backed values, the `.okc-personalize-target` opt-in for prose — appears in no authored page, no schema entry and no `oku spec` output. One passing word in a landing entry about the chrome cluster is the whole of its documentation. A primitive nobody can discover is not a primitive, and this is a shipped one, so it is on the board.

- The last chart that showed a reading and gave no way to keep it can keep it. `quadrant` draws dots and wires no cursor, so the reading on screen is the Cartesian dot path's own — and that path predates pinning entirely: it printed no offer and bound no click, which is why it was the only ● Tooltip in the table sitting beside a ○ Click-pin. The generalisation is small, because a pin with no anchor element already existed for the cursor and only needed a second user; what is new is that the dot is a distinct tooltip OWNER, so the host can tell "the dot wrote this" from "an anchor wrote this". That distinction is the whole safety argument: an anchor's click never reaches the host, so pinning one from a click on empty plot would be a surprise the reader did not ask for. The flag is named for what it holds now rather than for the writer that found it — a pin with no anchor, not a cursor pin. Click-pin is ● on 52 of 53, and the remaining — is `network`, whose gesture is a drag.

- Reviewing the pin work for collateral damage found two defects in it, and both were mine. **The close button stranded the chart.** It called `unpinRich`, which clears the ANCHOR pin and not the cursor's — so on a cursor pin it hid the tooltip and left `_tipPinned` true forever, and every cursor in the kit returns early on that. Measured on density: click the `×`, and the chart never answers the pointer again, with nothing on screen saying why. A control that silently stops the figure is worse than one that does nothing. **And Escape did nothing at all**, on a button whose own title reads `Close (Esc)`. The host's keydown only fires with focus inside the host; the anchor path gets that for free, because clicking a mark focuses it and every mark carries `tabindex`, and a cursor pin has no anchor — an `<svg>` is not focusable, so the click focused nothing and the key went to the document. Both go through one `unpinAny` now, which releases whichever kind is held, and taking a cursor pin moves focus to the tooltip's own close button, which is what makes the advertised key true. Verified failing against the previous kit on both releases and passing on this one; the anchor-pin case passes either way, which is what a regression guard is supposed to do. Worth naming the method rather than the fix: these came from re-reading the diff for interactions nobody had exercised, not from a report — the pin was landed with tests that all passed, and the combination "pinned, then click the control that closes it" was not among them.

- The interactivity table is the whole catalog now, and every cell in it was measured rather than recalled. It recorded 28 variants against a kit shipping 53, so a reader who took it for the catalog saw about half of one — and three of its footnotes had gone stale underneath it. The instrument matters here, because the first version of this measurement was wrong and I published nothing from it: it hovered charts on one shared 53-chart page and gave different answers on different runs. Each chart now gets its own page and its own page LOAD, so no earlier hover, pin or focus survives into the next reading, and every hover is confirmed to have landed before anything is read off it. The corrected run also caught a false negative in my own detector — the cursor column looked for the two classes the generic helper uses, and the kit draws seven, so ridgeline, sparkline, gauge and the three DIV bar charts came back as having no cursor. Those first four are exactly the ones the old footnote named as the sweep-axis charts, which is what made the mistake visible. What the run says: **Tooltip ● on all 53** and **Fullscreen ● on all 53**; **Click-pin ● on 51**, with `network` — because its gesture is a drag the kit deliberately makes no pin offer for, and `quadrant` ○ because it draws dots and no cursor and the dot path has no click of its own; **Hover-highlight ● on 21**; **Synced cursor ● on 26**. The old footnote's other two claims are gone with it — it said synced cursors only make sense for "Cartesian, ridgeline, sparkline, gauge" against 26 charts that have one, and implied the DIV bar variants have no fullscreen when all 53 carry the control. The measurement itself is committed as [`tools/chart_capabilities.py`](#f/tools/chart_capabilities.py), because the cells will need refreshing the next time a chart type lands and a number nobody can reproduce is a number nobody should trust. **And the table is held against the code now**, because a hand-maintained list beside a growing enum is exactly the drift that produced this row: `test_authority_agreement.py` checks that its rows are the chart types the kit ships, and that the two languages record the same marks. Row coverage only — whether a chart fades its siblings on hover is a browser measurement and stays in the browser suite; whether there is a row at all is a set comparison, and that is the half that rotted.

- Every tooltip in the kit prints `click to pin`, three different writers print it, and one of them never bound a click. `rich()` honours it for the anchors and the DIV bar charts honour it in `showCrossing`; `_showCursorTip` printed it into five call sites with nothing listening. Measured on density and bump: the hint rendered, a click pinned nothing, and moving the pointer away took the reading down. The cursor has no anchor to take the click — it places the tooltip at a coordinate, not against an element — so the host takes it, and the frozen cursor line is the indicator that a mark's `.okc-pinned` would otherwise be. One flag serves all five call sites, because `_tipPinned` is what every cursor already tests before it redraws. **Two more defects sat behind that one and only appeared once the click worked.** On a Cartesian chart the reading under the pointer is the cursor's cross-series readout while the pointer is physically on a dot, and clicking focused that dot: its `focus` handler swapped the readout for the single point's coordinates between the mouse going down and coming up — `Engineering cost ≈ 4 / Showstoppers + High 9` became `Showstoppers + High / H3 / (4, 9)` — so the click found a tooltip nobody had offered to pin. That handler answers `:focus-visible` now, which is the same rule the filepath chip's card controller already follows, and Tab still shows a dot its reading. Then the pin held and leaving the dot took it away, because the dot path's `hideTip` hid whatever was there — it predates pinning entirely, so nothing it did could disturb a pin until now. **And one mark makes no offer at all**: a network node is dragged, and `_wireNetworkDrag` calls `svg.setPointerCapture` on pointerdown, so every event after that goes to the SVG and the node never sees a mousedown, a mouseup or a click. Measured — `elementFromPoint` names the node's own `<circle>`, the click arrives at `svg.okc-svg`, and capture-phase listeners on the node group record nothing. The pin could never fire there, so the fix is to stop printing an offer the gesture cannot keep rather than to bolt a click onto a drag. One test per writer, not per chart: a 53-case sweep found the defect and then proved unfit to keep it — it hovers whichever mark it can reach on a crowded page, and on `arc` that answer moved between runs while arc pinned correctly three times out of three on a page of its own.

- The catalog research asked about five figures and the kit already draws all five; the row was a vocabulary mismatch, not a gap. Measured against three sources at once — the schema's `type` enum, [`kit/schema/examples.json`](#f/kit/schema/examples.json), and the renderer methods in chrome.js — **waterfall, marimekko and sunburst** are present in all three under exactly those names. The other two ship under different ones. **A joy plot is a ridgeline**: same figure, two names, and `ridgeline` is the neutral one — the renderer's own comment says its rows overlap by design, which is the whole of what the other name describes. **A dot matrix is the same unit-chart family as `waffle`**: segments filling a grid, one cell per unit, and the glyph is a rounded square rather than a dot. That last one is a styling difference and is stated as one rather than as equivalence — a reader who wants round marks wants a fill and a radius, not a chart type. So there is nothing to add, which is the answer the row was asking for. The same sweep surfaced something else worth writing down and not fixing here: the interactivity table above records 28 of the 53 chart types the kit ships, so a reader who takes it for the catalog sees roughly half of one. Its footer is scoped honestly — "all 28 variants recorded above" — and the table is still hand-maintained beside a kit that now has a test asserting every type answers the pointer. That is on the board.

- The two charts that answered the pointer with a line and no numbers now say something, and one of them had been saying nothing at all. Measured before: `density` drew a vertical cursor and had 0 marks carrying a payload and 0 native `<title>` elements; the horizontal `violin` had the same cursor and 0 payloads against 3 titles; and the VERTICAL violin — a separate renderer, reached by `orientation: vertical` and by no shipped example — wired no cursor either, its own comment saying a horizontal one would be the right affordance and no helper existed. So it answered with nothing. Each gets the reading its own shape can support. A violin's body carries the five-number summary the shape draws and never names — n, min, q1, median, q3, max — because the median line and the IQR box are already there and unlabelled; the vertical cursor over the rows stays an alignment aid with no reading of its own, which is the same division beeswarm already uses, and it is only safe because a reading now has an owner. Density has no mark to hover — it is one curve — so the cursor is the only reading it can have, and it reports the height as a share of its own peak and the share of observations at or below the cursor. **Both numbers describe the drawn picture rather than the KDE's units**: the plotted height IS `d / maxDensity`, and a raw density in units of 1/x formats badly and answers a question nobody asked — the kit's own `fmtNum` renders 0.0043 as `0.00`. One builder serves both violin orientations, because they share nothing else and two copies of a chart's reading is how two renderers stop agreeing about what the chart says. The sweep no longer skips anything: a chart with no mark now falls through to its cursor and must produce a reading there, so the two standing skips became a requirement and all 53 chart types pass. Writing the check found one thing worth keeping: JavaScript's `toFixed` rounds a tie away from zero and Python's `format` rounds half to even, which is not exotic here — it is every other quartile of a four-value distribution, and the test read the kit's correct median of 127 as a wrong 126 until it modelled the right rule.

- Three charts built a reading and never showed it, and the cause was one tooltip element with three writers and no rule about who owns it. Beeswarm, bump and horizon each wire a per-mark tooltip AND a vertical cursor. Hovering a mark built the tooltip with the right content — `Berlin · 2020 rank #1 value 80` on bump — and it never became visible. The anchor saw `mouseover` and `mouseenter` and no leave, the tooltip is `pointer-events: none` and did not overlap the mark, so nothing about the pointer explained it. What did: `_wireGenericVerticalCursor` calls `_hideCursorTip()` on the same branch where it hides its own line — a mousemove outside the plot band, on either axis — and a data mark can sit outside the band its own chart declares. Measured in viewBox units against the band the cursor line spans: beeswarm's leftmost dot at x=22 and horizon's first hit rect at x=65 are left of `pad.left`, and bump's top dot at y=34 is above a band top of 36. ## Locked decisions {#decisions}

Each was an open question once; collected here so future contributors don't relitigate.

- Project name = oku (Turkish 'read!'). Every layer reads `oku`: package (src/oku/), kit CSS prefixes (okt- / okc- / okd-), JS globals (__oku*), event names (oku:*), data-attrs (data-oku-*), and custom-element tag names.
- GitHub remote URL stays at github.com/mmdemirbas/html-doc — the schema $id, the git-clone example, and the jsdelivr CDN URL all point there. The local repo directory name follows the remote.
- Code / output columns inside example-pair MUST align at the top edge of the box. No 24px spacer for non-code outputs — the visible top edges of the code and output columns line up regardless of the output kind.
- Tooltip width is stable across pin states. Pinned vs unpinned switches the footer text + close-button visibility, NEVER the bounding box.
- ext-ref host is NOT a navigation link. Clicking pins the tooltip; the destination URL lives as a clickable domain anchor inside the citation card. One affordance per element.
- Pagefind is a Python dep, not a system binary — `oku[search]` extra pulls `pagefind[bin]>=1.5`.
- Layout = option A (centered document, three-mode content-width cycle: narrow / comfortable / max).
- Tier 3 viz (sankey / network / scatter-matrix / parallel-coordinates / chord / geo) all ship as kit-native chart types — no third-party chart library.
- Charts / tables / diagrams are sub-pages of Reference (meta.parent: 'reference').
- Source format = v3 markdown-first. A page is `.md`: YAML front-matter + a strict-GFM body (no indented code blocks, no setext headings, no lazy continuation — linted, still valid GFM); kit primitives are ```oku-<kind> fences with one compact JSON body; diagrams are ```mermaid fences with an italic caption line; raw block-level HTML islands (script included) pass through to the kit untouched and are audited by `oku check`. Decided after measuring tokens (markdown ≈ 20% leaner than v2 JSON, far leaner than HTML), LLM emission accuracy, and ecosystem direction; HTML-first was evaluated and rejected for repo-resident continually-edited sources. JSON pages (v1/v2) keep rendering via shims; `oku migrate` converts them.
- Build outputs = two trees (standalone, site). No dist/markdown twins — the .md sources are the canonical AI/LLM surface; llms.txt lives at the site docs root.
- Reactive prose (`${expr}` interpolation, `oku-bind` two-way binding) is **not being built**, and the reasons are not the ones assumed. It is not a capability gap: a built page has no CSP at all — measured, `new Function('return 6*7')()` returns 42 on a standalone page over `file://` — so an evaluator would run. And half of what the row asked for already ships under another name. `{{key}}` personalization substitutes reader-set values into prose at runtime (`kit.json` declares the keys, values persist in localStorage, `.okc-personalize-target` opts a prose passage in), and an HTML island in a page executes its own `<script>`, so two-way binding on a form input needs no new syntax today. What `${expr}` would add is a templating layer in the renderer and a second evaluation surface in a kit that spent real effort making a VIEWED document inert — against a format whose files are meant to stay readable on GitHub. That last cost is a matter of degree rather than a prohibition: `{#anchor}` and typed fences are already visible there, but they degrade to something a reader can still parse, and an expression sitting inside a sentence does not. **Reopen trigger:** authors asking for computed rather than supplied values. The cheaper answer then is derived keys in personalization, not an evaluator in prose.

## Principles {#principles}

Reader-, author-, and maintainer-facing rules every change honours.

- Single LEFT sidebar — TOC + site tree stacked. No right TOC, no mid-edge tab.
- Visual-first authoring. Pros/cons → comparison-cards, metrics → kpi-grid, trade-offs → table-with-chips. Paragraph + bullets is the fallback, not the default.
- Every fix pairs with a Playwright check. Browser-level fixes ship with numeric assertions captured in the commit body.
- Numbers in counters / badges only — no English words baked into the kit.
- No demo sibling pages. Every example for a primitive lives next to its heading.
- No process / round / historical references in docs — describe current behaviour, not how it got there.
- Layout invariants are numeric, not eyeball — express the rule as a boundingBox / computed-style assertion or accept it isn't a rule yet.
