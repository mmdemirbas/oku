# Bug hunt: the IntelliJ plugin and `oku preview --serve`, 2026-10-18

Scope: every Kotlin source under `src/main/kotlin`, `install.py`, and the
oku side the plugin talks to: `_preview_serve` and the request handlers in
`src/oku/cli.py` (`preview_page`, `check_buffer`, `fix_buffer`,
`registry_entries`, `heading_lines`, the greeting). Branch
`fix/plugin-bug-hunt`, from `dee0d7c`.

Baseline: plugin suite 48 tests green. Python: 3414 passed, 10 failed and
19 errors in a run that shared the machine with a Gradle build; the 11
failing files rerun alone gave 154 passed and 1 failed, the kit test
named under "Fixed after the merge".

## Fixed

Each is a `test(...)` commit that fails, then a `fix(...)` commit.

| Category | Defect | Trigger | Commits |
|---|---|---|---|
| IV.1 concurrent close | `restart()` took the lock a waiting request holds | Settings' Apply (EDT) while a request waits: 29969 ms frozen | `cb5a71d`, `486ca7d` |
| VI.2 error integrity | An oku that exited was reported as "did not answer within 30s" | oku stops at once, e.g. a broken install | `072dfde`, `f706ebb` |
| IX.1 stream parsing | Replies were read as "the next line", ignoring the echoed `id` | Any non-protocol line on oku's stdout; every later reply one behind | `59812e4`, `d31d923` |
| IV.5 cancellation | Registry and fix round trips could not be cancelled | Completion in a read action holds the read lock until oku answers; the fix's Cancel did nothing | `ef9756b`, `8620c4c` |
| V.5 unbounded cache | The registry cache kept every page's answer forever | Every page completed in, for the life of the IDE | `97e9af2`, `eed3895` |
| XI.1 stale state | All previews shared one `error.html`, loaded by one URL | Two failing previews show each other's reason; a second failure in one preview is skipped by JBCef | `df1995c` (refactor), `0129a27`, `9f27644` |
| VI.5 boundary | `SystemExit` ended the whole serve loop | `_read_shipped_schema` on a broken kit schema | `d8b4aee`, `2841694` |
| XII.1 monotonic time | Registry freshness was read off the wall clock | A clock set back makes every age negative: a stale answer is served and never pruned | `c5ce68f` (refactor), `405b926`, `1fc94ab` |

The IX.1 trigger was not observed in today's oku: check, fix, registry and
render requests on a tree with `skip_gitignored` printed protocol lines
only. The fix guards the contract, not an observed line.

The IV.5 fix in `OkuChipFix` had no test at first: the headless progress
gives a test no handle on the indicator to cancel. After the merge the
wait became `OkuChipFix.ask` (`cc581f1`), tested under an indicator the
test cancels (`37b81e6`); with the wait as a plain `get()` the case fails.

## Fixed after the merge

- **XII.1** is the last row of the table above. It was recorded here
  first because a failing test needed a clock seam the code did not have;
  `c5ce68f` adds the seam with no change in behaviour.
- **Kit test, outside the hunt's scope.**
  `browser/test_prism_asks_only_for_what_it_has.py::test_the_vendored_components_are_all_present`
  failed on a freshly vendored tree. `prism_components_needed` leaves out
  `css`, `javascript` and `markup` because `prism.min.js` bundles them,
  and the test asked for a file for every name in `_PRISM_LANGS`. It
  passed only in a checkout whose vendor cache predated the catalog. The
  test now asks for the components `oku vendor` fetches (`1336e61`):
  6/6 against the old cache and against a fresh one.

- **XI.1, `install.py`: a deploy trusted the Gradle watcher.**
  `build_plugin` ran `gradlew buildPlugin` without `--no-watch-fs`. In
  this hunt a daemon watching the file system called `compileKotlin`
  up to date over an edited source, and the tests ran the old class. In a
  deploy the same miss installs a zip of the old code and reports
  success. `89177df`, `ae25a1e`.

## Performance: the requests an edit makes

Measured with `tools/hot_paths.py` (one serve session, the page's own
text as the buffer, median of 7 warm requests) at load average 8-12. A
first run at load average 80, while another project's agents ran test
loops, gave numbers 4-20x higher and was discarded.

| Request | docs/reference.md | docs/index.md | plugin docs/index.md | 62-page tree (atolye/arastirma) |
|---|---|---|---|---|
| render | 147 ms | 22 ms | 115 ms | 35 ms |
| check | 213 ms | 177 ms | 59 ms | 525 ms |
| registry | 36 ms | 36 ms | 28 ms | 247 ms |
| fix | 217 ms | 179 ms | 56 ms | 522 ms |
| anchor | 6 ms | 0.6 ms | 18 ms | 1.4 ms |
| registry sent behind a check | 252 ms | 226 ms | 81 ms | 789 ms |

Changed, each a `test(...)` commit that fails and a `perf(...)` commit:

| Path | Change | Before → after | Commits |
|---|---|---|---|
| render | `_code_spans` found each inline span against every span before it (590,587 comparisons for reference.md); now bisects over fence starts | preview_page CPU, reference.md: 175 → 141 ms | `9b251f4`, `02aeb94` |
| completion, hover, navigation | registry and anchor go to a third process instead of queueing on the check session | registry during a check, 62 pages: 756 → 252 ms | `1d87edf`, `0d2bc81` |
| completion, hover | the registry's page list is kept per tree snapshot instead of a manifest per request | registry, 62 pages: 245 → 7.8 ms | `3cdea70`, `3f4a6af` |

The third process holds about 38 MB resident after a registry and an
anchor request.

### Recorded, not changed

- **A carried file's text is rewritten.** `_asset_hrefs` and
  `_rewrite_assets` walk the whole page dict, `m._files` included. A file
  a chip carries that writes `![x](dot.svg)` has that href replaced by a
  data: URI when the page also carries `dot.svg` (run: a two-file tree,
  `oku preview`, the carried `notes.md` holds `data:image/svg` and no
  longer `(dot.svg)`), so the viewer's source view is not the file. The
  same rewrite is what shows that image in a viewed file on a standalone
  page, when the href happens to name the same file. Which one should
  hold is a decision about viewed files' images, in kit code another
  session is changing. The walk is also most of the render's text:
  reference.md's carried files are 460 KB against 49 KB of the page.
- **The check lints the whole tree on every request.** Needed for the
  findings about other pages; 525 ms on 62 pages. A per-page lint result
  kept by content would cut it to the page; not attempted, since it
  changes how `check_pages` is fed.
- **The fix costs a check.** By design: it applies what the check reports.
